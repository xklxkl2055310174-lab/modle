# 面试说明

**这个项目解决什么问题？** 把固定小模型变成可观测、可承压、可解释的 HTTP 推理服务。能展示接口、执行调度和测量方法，不能把学习项目说成生产平台。

**为什么 asyncio 里仍需要线程？** asyncio 适合等待和调度；图片解码与推理占用 CPU/GPU，直接执行会阻塞健康检查和其他请求。专用线程让事件循环保持响应。吞吐是否提高必须由实际数据决定。

**动态批处理为什么可能改善吞吐，却恶化 P99？** 批处理摊薄固定开销、改善算子利用率，同时增加等待凑批时间。低并发下往往凑不满；大批还可能带来显存压力。根据成功 QPS 和成功 P99 的曲线选参数，不只追最大 batch。

**线程池和进程池有什么差别？** PyTorch 原生算子可释放 GIL，线程可共享模型，但存在内部线程过度订阅。spawn 进程独立初始化避免 fork 后运行时状态问题，同时增加模型副本、内存、序列化和启动成本。三种模式使用相同 API、队列和指标，便于公平比较。

**超时能中断 GPU kernel 吗？** 不能。Future 超时只结束调用方等待。排队中的过期任务跳过；已执行任务仍运行到完成。这解释了为什么超时不能替代限流和有界队列，也解释了强制停机需要进程监督。

**怎样防止一个坏图片拖垮整批？** 单独解码/校验图片；推理非 OOM 错误时按样本重试一次；CUDA OOM 拆小批。每个 Future 独立返回成功或失败，响应记录实际成功子批大小。

**怎么证明 CPU 打满就是瓶颈？** 单一 CPU 百分比不足够。结合吞吐是否平台化、P99、上下文切换、线程栈和算子分布；减少线程后重复测量。CPU 很高也可能是有效计算，低 CPU 也可能是锁或 IO 等待。

**为什么同时报告失败率和两种 P99？** 限流会快速失败，降低包含失败请求的总体 P99；真正被接受的请求可能没有改善。必须联合成功 QPS、成功 P99、全部请求 P99、拒绝率、队列和资源看结果。

**这个项目还有哪些边界？** 单实例令牌桶、没有认证、没有跨机调度、Python 不能安全抢占原生线程。GPU、Docker/JMeter、完整并发矩阵和 30 分钟稳定性验证状态看 PROGRESS。仅能在简历中引用 report.md 中真实且附原始数据的结论。
